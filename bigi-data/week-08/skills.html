Why a history beats a folder of copies

Waarom een geschiedenis beter is dan een map met kopieën

Most people keep versions by copying files: report.docx, report_v2.docx, report_final.docx. The copies keep the old text. They lose the rest: which lines changed between two versions, why they changed, who changed them and when.

De meeste mensen bewaren versies door bestanden te kopiëren: rapport.docx, rapport_v2.docx, rapport_definitief.docx. De kopieën bewaren de oude tekst. De rest raken ze kwijt: welke regels tussen twee versies veranderden, waarom, wie ze veranderde en wanneer.

Git keeps a project's history as a chain of snapshots called commits. Each commit records the state of every file in the project, a message, the author and the time. Because each commit knows the one before it, git can show the exact difference between any two versions, bring back any earlier state, and say who last changed any line.

Git bewaart de geschiedenis van een project als een keten van momentopnamen die commits heten. Elke commit legt de toestand van elk bestand in het project vast, met een bericht, de auteur en het tijdstip. Omdat elke commit de vorige kent, kan git het precieze verschil tussen twee versies tonen, elke eerdere toestand terughalen, en zeggen wie een regel het laatst veranderde.

Git and GitHub are two different things. Git is the program that keeps the history on your own computer, with no internet needed. GitHub is a website that keeps a copy of the history online and adds the parts that involve other people: accounts, permissions, pull requests and pages anyone can read.

Git en GitHub zijn twee verschillende dingen. Git is het programma dat de geschiedenis op je eigen computer bijhoudt, en het heeft geen internet nodig. GitHub is een website die een kopie van de geschiedenis online bewaart en de onderdelen toevoegt waar andere mensen bij komen kijken: accounts, rechten, pull requests en pagina's die iedereen kan lezen.

Four places a change can be

Vier plekken waar een wijziging kan zijn

A change moves through four places, and each git command moves it one step.

Een wijziging gaat langs vier plekken, en elke git-opdracht brengt haar één stap verder.

  • The working folder holds the files as they are on disk right now.De werkmap bevat de bestanden zoals ze nu op de schijf staan.
  • The staging area holds the changes you chose for the next commit, and git add puts a file there.De staging area bevat de wijzigingen die je voor de volgende commit hebt gekozen, en git add zet een bestand daar.
  • The repository holds the history, and git commit turns everything staged into one snapshot.De repository bevat de geschiedenis, en git commit maakt van alles wat klaarstaat één momentopname.
  • The remote is the shared copy, usually on GitHub and named origin. git push sends your new commits there, and git pull brings down commits that others pushed.De remote is de gedeelde kopie, meestal op GitHub en met de naam origin. git push stuurt je nieuwe commits daarheen, en git pull haalt commits op die anderen pushten.

Nothing is in a commit until you add it, and nothing reaches your team until you push. git status says where every file stands and, in its own words, which command comes next. Read it before every commit.

Niets zit in een commit voordat je het toevoegt, en niets bereikt je team voordat je pusht. git status zegt waar elk bestand staat en, in eigen woorden, welke opdracht daarna komt. Lees het vóór elke commit.

Reading a diff

Een diff lezen

A diff shows only the lines that differ between two versions of a file. A line that starts with a minus sign was removed, and a line that starts with a plus sign was added. An edited line shows up as one of each.

Een diff laat alleen de regels zien die tussen twee versies van een bestand verschillen. Een regel die begint met een minteken is verwijderd, en een regel die begint met een plusteken is toegevoegd. Een bewerkte regel verschijnt als één van elk.

Above each block of changes sits a hunk header such as @@ -12,4 +12,5 @@. The block starts at line 12 in both files. It runs for four lines in the old file and for five in the new one.

Boven elk blok wijzigingen staat een hunk-header zoals @@ -12,4 +12,5 @@. Het blok begint in beide bestanden op regel 12. In het oude bestand is het vier regels lang en in het nieuwe vijf.

Messages that say why

Berichten die zeggen waarom

Every commit needs a message, and the messages decide whether the history is worth reading. Six months later, you are the stranger reading them.

Elke commit heeft een bericht nodig, en de berichten bepalen of de geschiedenis het lezen waard is. Zes maanden later ben jij de buitenstaander die ze leest.

  • The subject is short. It has 50 characters or fewer and fits on one line of the log.De onderwerpregel is kort. Hij heeft 50 tekens of minder, zodat hij op één regel van het logboek past.
  • The subject is a command. It completes the sentence If applied, this commit will ..., so Skip days with no count works and Skipped days does not.De onderwerpregel is een opdracht. Hij staat in de gebiedende wijs, dus Sla dagen zonder telling over werkt en Dagen overgeslagen niet.
  • The subject names the change. Update README.md and fix stuff tell a reader nothing, so replace GitHub's default subject every time.De onderwerpregel noemt de wijziging. Update README.md en dingen gefikst zeggen een lezer niets, dus vervang de standaardregel van GitHub elke keer.
  • The body says why. After a blank line, one or two sentences give the reason when the subject cannot.De toelichting zegt waarom. Na een lege regel geven één of twee zinnen de reden als de onderwerpregel dat niet kan.
  • One commit holds one change. A subject that needs the word and describes two commits.Eén commit bevat één wijziging. Een onderwerpregel die het woord en nodig heeft, beschrijft twee commits.

History as evidence

De geschiedenis als bewijs

A result changes whenever the analysis changes. When a report quotes a number, a reader will ask which version of the analysis produced it. The history answers that question when the result file is committed together with the code that made it.

Een resultaat verandert telkens wanneer de analyse verandert. Als een rapport een getal noemt, vraagt een lezer welke versie van de analyse het opleverde. De geschiedenis beantwoordt die vraag als het resultaatbestand samen met de code die het maakte is gecommit.

Given a file name, git log lists every commit that changed that file. git show prints the file as it was in any one of them. A tag such as report-1 names one commit and saves the next reader the search.

Met een bestandsnaam erbij toont git log elke commit die dat bestand veranderde. git show drukt het bestand af zoals het in een van die commits was. Een tag zoals report-1 geeft één commit een naam en bespaart de volgende lezer het zoeken.

Branches

Branches

A branch is a name that points at a commit. When you commit on a branch, its name moves forward and main stays where it was, so a half-finished idea never reaches the version the team relies on. When the idea works, git merge brings its commits into main, and the branch name can be deleted.

Een branch is een naam die naar een commit wijst. Als je op een branch commit, schuift de naam mee en blijft main waar hij was, zodat een half af idee nooit de versie bereikt waarop het team vertrouwt. Als het idee werkt, haalt git merge de commits naar main, en kan de naam van de branch weg.

Working with a team

Werken met een team

On GitHub, the owner of a repository can add teammates as collaborators, who can then push to it. A pull request is a page that proposes the commits on a branch for main. It shows the diff, holds the review, and records the decision. For a small team, the habit that matters most is to pull before you push.

Op GitHub kan de eigenaar van een repository teamgenoten toevoegen als collaborators, die er daarna naar kunnen pushen. Een pull request is een pagina die de commits op een branch voorstelt voor main. Hij toont de diff, bevat de review en legt het besluit vast. Voor een klein team is de belangrijkste gewoonte: pull voordat je pusht.

Git stops and marks both versions in the file when two people change the same line, because it cannot know which text is right. Resolving the conflict means reading both versions, writing what the line should say, deleting the markers and committing. Keeping one side by reflex can throw away a fact the other person added.

Als twee mensen dezelfde regel veranderen, kan git niet weten welke tekst klopt, dus stopt het en markeert het beide versies in het bestand. Het conflict oplossen betekent: beide versies lezen, schrijven wat de regel moet zeggen, de markeringen wissen en committen. Wie uit gewoonte één kant houdt, kan een feit weggooien dat de ander toevoegde.

A README a stranger can follow

Een README die een buitenstaander kan volgen

GitHub shows the file README.md on a repository's front page, so every visitor reads it first. It is written in Markdown, where a line that starts with # becomes a heading. A README a stranger can follow answers five questions.

GitHub toont het bestand README.md op de voorpagina van een repository, dus elke bezoeker leest het als eerste. Het is geschreven in Markdown, waarin een regel die begint met # een kop wordt. Een README die een buitenstaander kan volgen, beantwoordt vijf vragen.

  • What is this project, and what question does it answer?Wat is dit project, en welke vraag beantwoordt het?
  • Where did the data come from, with a link and the date it was downloaded?Waar komt de data vandaan, met een link en de datum van downloaden?
  • How do I run it, step by step?Hoe voer ik het uit, stap voor stap?
  • What is in the folder?Wat zit er in de map?
  • What did the project find, and what is still unknown?Wat vond het project, en wat is nog onbekend?

The test is to hand the repository to someone who has never seen it. The README works when they can run the project and say what it found without asking you a question.

De test is de repository te geven aan iemand die hem nooit heeft gezien. De README werkt als die persoon het project kan uitvoeren en kan zeggen wat het vond, zonder jou iets te vragen.

What never goes in a repository

Wat nooit in een repository komt

A commit is permanent in practice. A file deleted in a later commit is still in the commits before it, and everyone who pulled holds a copy. On a public repository, anyone on the internet may hold one too. Four kinds of file stay out of every commit.

Een commit is in de praktijk blijvend. Een bestand dat in een latere commit is verwijderd, staat nog in de commits ervoor, en iedereen die pullde heeft een kopie. Bij een openbare repository kan iedereen op internet er ook een hebben. Vier soorten bestanden blijven uit elke commit.

  • Passwords, tokens and keys never go in. Keep them in a file such as .env that git is told to ignore.Wachtwoorden, tokens en sleutels gaan er nooit in. Bewaar ze in een bestand zoals .env dat git moet negeren.
  • Personal data stays out. Names, addresses and records about people stay out of a repository unless the people agreed and the law allows it.Persoonsgegevens blijven erbuiten. Namen, adressen en gegevens over mensen blijven uit een repository, tenzij die mensen instemden en de wet het toestaat.
  • Large files stay out. GitHub warns about any file larger than 50 MiB. It blocks files larger than 100 MiB (GitHub Docs).Grote bestanden blijven erbuiten. GitHub waarschuwt bij elk bestand groter dan 50 MiB. Bestanden groter dan 100 MiB blokkeert het (GitHub Docs).
  • Files a computer makes for itself stay out. Examples are .DS_Store, __pycache__ and .ipynb_checkpoints.Bestanden die een computer voor zichzelf maakt, blijven erbuiten. Voorbeelden zijn .DS_Store, __pycache__ en .ipynb_checkpoints.

A file called .gitignore lists the patterns git should never stage, so even git add . skips them. Write it before the first commit. If a secret does reach a pushed commit, treat it as leaked and change it at once. GitHub's own guide names revoking or rotating the secret as the first step (GitHub Docs).

Een bestand met de naam .gitignore bevat de patronen die git nooit mag klaarzetten, zodat zelfs git add . ze overslaat. Schrijf het vóór de eerste commit. Als een geheim toch in een gepushte commit terechtkomt, behandel het dan als gelekt en verander het meteen. De eigen handleiding van GitHub noemt het intrekken of vervangen van het geheim als eerste stap (GitHub Docs).

Commands to stop and read before you run them

Opdrachten waarbij je stopt en leest voordat je ze uitvoert

An AI assistant gives you a command that answers the question you asked. It may not think about your teammates or your secrets. Before you run any of these commands, ask what it will change or erase.

Een AI-assistent geeft je een opdracht die de vraag beantwoordt die je stelde. Hij denkt daarbij misschien niet aan je teamgenoten of je geheimen. Vraag bij elk van deze opdrachten wat ze zullen veranderen of wissen voordat je ze uitvoert.

  • git push --force replaces the shared history with yours and erases commits that others pushed.git push --force vervangt de gedeelde geschiedenis door de jouwe en wist commits die anderen pushten.
  • git reset --hard throws away every change you have not committed.git reset --hard gooit elke wijziging weg die je nog niet hebt gecommit.
  • git clean -fd deletes every untracked file in the folder.git clean -fd wist elk bestand in de map dat git niet volgt.
  • git add . stages everything git does not ignore, including a password file if no .gitignore lists it.git add . zet alles klaar wat git niet negeert, ook een wachtwoordbestand als geen .gitignore het noemt.
  • git rebase on a branch that others use rewrites commits they already have.git rebase op een branch die anderen gebruiken, herschrijft commits die zij al hebben.
  • A remote address with a token pasted into it saves the token in the folder's settings.Een remote-adres waarin een token is geplakt, bewaart die token in de instellingen van de map.

When the AI is wrong

Wanneer de AI zich vergist

In the notebook, Ana's push was rejected because Ben had pushed a commit she did not have. An AI assistant told her to run git push --force. The command ran without an error and erased 1 commit of Ben's from the shared history. Git's own refusal had named the safe path, which was to pull Ben's work first.

In het notebook werd de push van Ana geweigerd omdat Ben een commit had gepusht die zij niet had. Een AI-assistent zei dat ze git push --force moest uitvoeren. De opdracht draaide zonder foutmelding en wiste 1 commit van Ben uit de gedeelde geschiedenis. De weigering van git zelf had de veilige weg al genoemd: eerst het werk van Ben binnenhalen.

In a second case, Ana asked how to save all her work and share it. The assistant answered with git add ., a commit and a push. That sent a password file to the shared copy, together with a raw export of 2.1 MB. Ana then removed both files in a new commit. The password was still readable from the history. The stored history still measured 1.1 MB.

In een tweede geval vroeg Ana hoe ze al haar werk kon opslaan en delen. De assistent antwoordde met git add ., een commit en een push. Daarmee ging een wachtwoordbestand naar de gedeelde kopie, samen met een ruwe export van 2,1 MB. Ana verwijderde daarna beide bestanden in een nieuwe commit, en het wachtwoord was nog steeds leesbaar in de geschiedenis. De opgeslagen geschiedenis mat nog steeds 1,1 MB.

Both commands did what they were built to do. The assistant answered the question it was asked and never said what the commands would erase or publish. One habit catches both cases: read git status, and ask what a command will change before you run it.

Beide opdrachten deden waarvoor ze gemaakt zijn. De assistent beantwoordde de vraag die hij kreeg en zei nergens wat de opdrachten zouden wissen of publiceren. Eén gewoonte vangt beide gevallen: lees git status, en vraag wat een opdracht verandert voordat je hem uitvoert.

Het notebook draait git in een oefenmap. Doe deze stappen ook op GitHub zelf, want de workshops en de studio bouwen erop.

QuestionVraag 1

Ana commits a file that holds a password and pushes it. An hour later she deletes the file in a new commit and pushes again. What is true?

Ana commit een bestand met een wachtwoord en pusht het. Een uur later verwijdert ze het bestand in een nieuwe commit en pusht opnieuw. Wat klopt?

  1. The password is gone, because the newest commit no longer has the file.Het wachtwoord is weg, omdat de nieuwste commit het bestand niet meer heeft.
  2. The password is still in the earlier commit, so it must be treated as leaked and changed.Het wachtwoord staat nog in de eerdere commit, dus het moet als gelekt worden behandeld en veranderd.
  3. The password is safe if the repository is private.Het wachtwoord is veilig als de repository privé is.
